01 Le problème

Une app qui marche
≠ une app transmissible

L'API et l'app mobile fonctionnent, en démonstration, sur ma machine, déployées à la main. C'est exactement le point faible que ce module vient combler.

Ce que MP3 + MP4 prouvent

Le code est correct : architecture en couches, tests, sécurité applicative. Ça répond à « est-ce que ça marche ? ».

Ce qu'ils ne prouvent pas

Que quelqu'un d'autre que moi peut le déployer, le reconstruire après une panne, ou y toucher sans casser la production.

La vraie question de MP5

Si je disparais du projet demain, une autre personne peut-elle reprendre, en combien de temps, avec quels documents ?

Un déploiement fait à la main, une seule fois, par la seule personne qui connaît le projet : ce n'est pas un déploiement, c'est un secret. L'industrialisation, c'est transformer ce secret en procédure reproductible et documentée.

Conduite

Ne présente pas ça comme un aveu de faiblesse du MP3/MP4 : c'était hors périmètre de ces modules, dont le sujet portait sur l'API et l'app, pas sur l'infrastructure. Ici, c'est le sujet.

Si on demande « comment déployiez-vous avant ce module ? » : à la main, sur un poste de développement, sans procédure écrite ni preuve de reproductibilité. C'est précisément ce point de départ que la slide suivante détaille.

02 Point de départ

Ce qui existait
avant ce module

Acquis des modules précédents

  • logichain-api : API REST Node.js/TypeScript, MongoDB, architecture N-Tier, 65 tests
  • LogiChainMobile : application React Native, offline-first, 633 tests
  • Les deux consomment le même contrat d'API, sans modification depuis MP3

Ce qui manquait

  • Aucun provisionnement automatisé : la cible était configurée à la main
  • Aucune CI/CD : aucun contrôle avant fusion, aucun déploiement déclenché
  • Aucune protection Git : rien n'empêchait un push direct sur la branche livrée
  • Aucun document de passation : le projet tenait dans une seule tête
Ce module ajoute un troisième dépôt, logichain-infra, dédié à ce manque. Il ne touche ni au code de l'API ni à celui de l'app : il les provisionne, les déploie, et documente comment quelqu'un d'autre en fait autant.

Conduite

Cette slide sert de repère commun avec le jury qui a suivi MP3 et MP4 : dis explicitement « ceci, vous le connaissez déjà ; ceci est nouveau ».

Si on demande pourquoi ne pas avoir fait ça dès le MP3 : le sujet de MP3 portait sur l'architecture de l'API elle-même, pas sur son exploitation. Traiter l'infrastructure en étalant les responsabilités sur trois modules distincts, c'est aussi une décision de découpage assumée — chaque module a un objet clair.

04 La contrainte de départ

Pourquoi la cible
est une machine vierge

Une décision structurante, prise avant d'écrire la moindre tâche Ansible, et qui explique presque tous les choix qui suivent.

Le VPS existant est mutualisé

J'ai un VPS OVH réel, déjà en production pour d'autres projets, avec Docker et Traefik installés pour router plusieurs applications sur les mêmes ports 80/443. Y installer Nginx en direct entrerait en conflit de ports avec l'existant, et un rôle Ansible qui réécrit sa configuration système risquerait un projet qui n'est pas le mien.

La solution : une cible neutre

Le playbook est écrit pour une machine dédiée et vierge : Ubuntu 24.04 fraîche, sans rien d'installé. En local, c'est une VM Multipass. En CI/CD, c'est un runner GitHub jetable. Le VPS mutualisé reste un futur inventaire (prod), pas la cible d'aujourd'hui.

Cette contrainte est la raison directe de la slide 19 : si le playbook ne fonctionne que sur une machine déjà à moitié configurée par moi, il ne prouve rien. Il doit fonctionner sur une machine qui n'a jamais rien vu — c'est ce que je démontre en direct.

Conduite

Assume-la comme une décision d'ingénieur, pas comme une excuse. Le jury connaît probablement ce genre de contrainte réelle (VPS mutualisé, budget limité) : elle rend le projet plus crédible, pas moins.

Si on demande « pourquoi ne pas avoir pris un second VPS ? » : coût, pour un projet noté sans budget dédié. Multipass et le runner GitHub Actions sont gratuits et suffisent à prouver l'automatisation ; le jour où un vrai budget existe, le même playbook s'applique tel quel à un VPS dédié — c'est justement l'intérêt d'un provisionnement scripté plutôt que manuel.

L'argument n'est pas « trois dépôts, c'est plus propre ». C'est que chaque dépôt n'exige que ce qui le concerne réellement : logichain-infra n'a pas de suite de tests applicatifs, donc son ruleset n'exige pas le check « Qualité et tests » — l'exiger aurait bloqué toute Pull Request en attente d'un contrôle qui ne peut techniquement pas se déclencher. Trois dépôts, trois cycles de vie, trois exigences de vérification adaptées, plutôt qu'un monorepo où un seul jeu de règles s'appliquerait mal à tout le monde.

Conduite

Le tableau, colonne de droite, est ta preuve : les rulesets réels des trois dépôts n'exigent pas les mêmes checks, précisément parce que logichain-infra n'a rien à tester au sens applicatif. C'est vérifiable dans soutenance/preuves/rulesets-full.json.

Si on demande « pourquoi pas un monorepo ? » : trois cycles de déploiement différents (l'API se déploie, l'app se publie, l'infra se provisionne) et trois historiques de commits qui n'ont pas de raison de se mélanger. Le lien entre eux, c'est CONTRIBUTING.md, partagé à l'identique dans les trois.

06 Gouvernance

Gitflow simplifié

main        ●───────────────●───────────●───────────►  (livrable — un push déclenche cd.yml)
             \               \           \
develop       ●───●───●───●───●───●───●───●─────────►  (intégration continue)
               \   \       \
feature/*       ●───●       ●─────────►  (une évolution, courte durée de vie)

hotfix/*    part de main, revient sur main ET develop

main

Reflète toujours l'état livrable. Historique linéaire imposé. Un push y déclenche le déploiement continu — jamais de push direct, toujours par Pull Request fusionnée.

develop

Branche d'intégration : tous les feature/* y fusionnent avant de partir vers main.

Conduite

Le schéma se lit comme celui de MP3/MP4, s'ils en avaient un — insiste sur la spécificité infra : un push sur main n'est pas anodin ici, il déploie réellement. C'est pour ça que main est la branche la plus protégée des trois dépôts.

Si on demande pourquoi pas de release/* classique du Gitflow historique : le projet n'a pas de cycle de release séparé de la fusion vers main — chaque fusion vers main EST une release, déployée immédiatement. Ajouter une branche release/* intermédiaire n'aurait rien apporté à l'échelle du projet.

07 Gouvernance

Un push direct
ne passe pas

Six rulesets GitHub actifs — deux par dépôt (protection-main, protection-develop) — empêchent toute évolution du code hors Pull Request.

$ git push origin main
remote: error: GH013: Repository rule violations found for refs/heads/main.
remote:
remote: - Changes must be made through a pull request.
remote:
remote: - 2 of 2 required status checks are expected.
remote:
 ! [remote rejected] main -> main (push declined due to repository rule violations)
error: failed to push some refs to 'https://github.com/Fulkiaaa/logichain-api.git'

Ce que chaque ruleset impose

Suppression et non-fast-forward interdits, historique linéaire sur main, threads de revue résolus, et le check requis vert avant fusion. Aucun acteur de contournement (bypass_actors: []) — la règle s'applique aussi à la propriétaire du dépôt.

La revue différée, assumée

required_approving_review_count vaut 0 aujourd'hui : projet en solo, et GitHub interdit d'approuver sa propre Pull Request — l'exiger à 1 aurait bloqué toute fusion. Documenté dans CONTRIBUTING.md §8 : c'est la première action de la passation, dès un second contributeur.

Conduite

La capture est réelle : soutenance/preuves/push-rejete-api-main.txt, un push direct tenté sur logichain-api pendant la Tâche 13. Précise que c'est un test délibéré, pas un accident.

Le bandeau du deck passe en « CI en cours » sur cette slide : c'est l'état réel capturé dans pr-develop-main-blocked.json, une Pull Request bloquée parce que ses checks étaient encore IN_PROGRESS — pas en échec, simplement pas encore terminés. La même Pull Request redevient CLEAN une fois les checks au vert (pr-develop-main-green.json).

Si on demande « et si le check tombe en panne durablement ? » : CONTRIBUTING.md §9 documente la procédure d'urgence — désactiver temporairement le ruleset depuis l'interface ou en ligne de commande, jamais pour contourner un échec légitime, toujours réactivé ensuite.

Si on demande pourquoi 0 approbation n'est pas une faille : parce que la contrepartie existe déjà ailleurs — le check CI obligatoire, gitleaks, et le fait que la propriétaire elle-même ne peut pas contourner le ruleset. Ce n'est pas « aucune protection », c'est « la protection humaine viendra avec l'équipe ».

08 Gouvernance

Un hook natif,
pas Husky

Les trois dépôts partagent la même convention (<type>(<portée>): <résumé>), mais logichain-infra l'applique différemment, pour une raison concrète.

Pourquoi pas Husky ici

logichain-api et LogiChainMobile installent Husky, qui a besoin d'un package.json déjà présent chez eux. logichain-infra est un dépôt Ansible pur : en ajouter un uniquement pour Husky introduirait une dépendance Node.js superflue.

Le hook réel

.githooks/commit-msg, un script shell versionné sans dépendance, activé une fois par clone (git config core.hooksPath .githooks). commitlint.config.js reste présent pour la cohérence documentaire, mais ce n'est pas lui qui bloque.

$ git commit -m "message invalide sans type"
✖ Message de commit invalide : « message invalide sans type »
  Format attendu : <type>(<portée optionnelle>): <résumé>
[rejeté, exit 1]

$ git commit -m "docs: test du hook commit-msg"
[main (root-commit) 774f6fc] docs: test du hook commit-msg
[accepté, exit 0]

Conduite

La sortie ci-dessus vient réellement du Runbook (§10.3) : testée dans un dépôt Git jetable avec une copie du même hook, pour ne prendre aucun risque sur l'historique réel.

Si on demande pourquoi ne pas avoir simplement créé un package.json vide pour Husky : ça aurait fonctionné, mais introduit un outillage Node.js (npm install, node_modules) dans un projet qui n'en a besoin nulle part ailleurs — un coût de maintenance pour un seul hook. Le script shell fait exactement la même vérification avec zéro dépendance.

10 Choix technique

Ansible,
pas Terraform

Les deux outils sont complémentaires plus que concurrents, mais un seul répond à la contrainte réelle de ce projet : configurer une machine qui existe déjà.

BesoinTerraformAnsible
Rôle typiqueCréer/détruire des ressources cloud (VM, réseau, DNS…) via une API de providerConfigurer un système déjà existant : paquets, utilisateurs, fichiers, services
Accès requis à la cibleAPI du cloud providerSSH seul, agentless

La cible de ce projet, qu'elle soit une VM Multipass locale ou un futur VPS OVH, existe déjà — il n'y a rien à provisionner au sens cloud. Le besoin est de la configurer de façon reproductible : c'est le métier d'Ansible, pas de Terraform.

Conduite

Ne dénigre pas Terraform : les deux sont utilisés ensemble dans beaucoup de projets réels (Terraform crée la VM, Ansible la configure). Ici, la VM est créée par Multipass en une commande ou existe déjà (VPS OVH) : il n'y a pas de couche de provisionnement cloud à automatiser.

Si on demande « et si demain vous passez sur AWS ? » : Terraform prendrait alors tout son sens pour créer l'instance ; le playbook Ansible, lui, resterait identique — il ne connaît que du SSH et un système Ubuntu 24.04, peu importe qui l'a créé.

12 Rôle : system_security

L'ordre du pare-feu
n'est pas arbitraire

Le piège évité

Les autorisations de ports (22, 80, 443) sont posées avant la politique deny incoming et avant l'activation d'UFW. Inverser cet ordre coupe la session SSH en cours au moment même de l'activation du pare-feu — la machine devient inaccessible, il faut la détruire et recommencer.

Le reste du rôle

Utilisateur de service sans mot de passe (accès par clé uniquement), configuration SSH validée avant écriture (validate: sshd -t -f %s — une faute de frappe ne coupe jamais l'accès), Fail2Ban sur sshd, mises à jour de sécurité automatiques.

Bug rencontré sur machine vraiment vierge. sshd -t exige que /run/sshd existe pour valider une configuration — même en lecture seule. Sur la VM Multipass, ce répertoire existe déjà (sshd tourne en continu depuis le premier démarrage). Sur un runner GitHub neuf, /run est un tmpfs vierge et sshd n'a jamais démarré : la validation échouait avec Missing privilege separation directory: /run/sshd. Corrigé en créant ce répertoire explicitement avant la validation — invisible en local, systématique en CI.

Conduite

C'est le premier des bugs de machine vierge que tu racontes en détail : garde-le concret, il illustre parfaitement pourquoi un second environnement (le runner CI) a une valeur qu'une seule VM familière n'a pas.

Si on demande pourquoi ne pas avoir découvert ça en local d'abord : parce qu'en local, la VM avait déjà démarré sshd au moins une fois avant que ce rôle ne soit rejoué — le bug ne se manifeste que sur une machine qui n'a jamais eu de sshd actif, ce qu'un runner GitHub neuf est à chaque exécution et qu'une VM de développement réutilisée n'est presque jamais.

13 Rôle : database

MongoDB en replica set
à un seul membre

Un choix qui surprend au premier regard : un replica set d'un seul nœud n'apporte aucune tolérance de panne. Il existe pour une autre raison.

Pourquoi rs0 quand même

L'API exige ?replicaSet=rs0 dans son URI de connexion pour ses transactions multi-documents (l'allocation ACID présentée en MP3). MongoDB ne les autorise qu'en replica set. Le module mongodb_replicaset valide par défaut au moins 3 membres votants : désactivé explicitement (validate: false), documenté en commentaire pour la prochaine personne qui lira ce rôle.

L'amorçage, en deux temps

1. mongod démarre sans authentification, le replica set s'initie, l'administrateur et l'utilisateur applicatif sont créés. 2. mongod redémarre avec authentification activée. Un marqueur sur disque (.ansible-bootstrapped) garantit que cette phase ne se rejoue jamais après le premier passage.

Deux index applicatifs créés au provisionnement : idx_items_qrcode (unique, sur items.qrCode — c'est lui qui rend le scan instantané côté mobile) et idx_events_status_start. Le module vérifie leur existence avant d'agir : toujours joué, toujours idempotent.

Conduite

Le point contre-intuitif à expliquer clairement : un replica set à un membre n'est pas de la haute disponibilité. Précise-le avant qu'on te pose la question, sinon elle viendra sous forme de piège.

Si on demande pourquoi ne pas avoir simplement utilisé Mongo en mode standalone sans authentification inter-nœuds compliquée : parce que l'API a été conçue en MP3 pour des transactions ACID, qui exigent un replica set. Changer ça reviendrait à modifier le contrat de l'API — hors périmètre de ce module.

Si on demande le rôle du keyFile : MongoDB exige une authentification inter-nœuds dès que authorization: enabled est combiné à un replica set, même à un seul membre. Généré une fois sur la cible (jamais transmis, jamais écrit sur le contrôleur), force: false pour qu'il ne soit jamais régénéré au passage suivant.

14 Rôle : web_proxy

Nginx : TLS,
et rien d'autre exposé

Ce que Nginx fait

  • Termine le TLS : certificat auto-signé en staging (web_proxy_tls_mode: selfsigned), régénéré uniquement si absent
  • Redirige le port 80 vers 443
  • Proxifie vers 127.0.0.1:3000, seul port où l'API écoute
  • /health exclue de la journalisation d'accès (access_log off)

En-têtes de sécurité déployés

  • Strict-Transport-Security : max-age=31536000; includeSubDomains
  • X-Content-Type-Options: nosniff
  • Referrer-Policy: strict-origin-when-cross-origin
  • server_tokens off : version de Nginx non divulguée
MongoDB n'écoute que sur 127.0.0.1 : jamais exposé directement, seule l'API y accède en local. Nginx expose le seul point d'entrée public utile. Détail de portabilité réel : Ubuntu 24.04 fournit Nginx 1.24, où http2 on; séparé n'existe pas encore — la syntaxe listen 443 ssl http2; a été utilisée à la place, seule prise en charge par cette version.

Conduite

Le détail Nginx 1.24 est un bon exemple de « portabilité vérifiée, pas supposée » : la directive la plus récente aurait fait échouer nginx -t sur cette version précise.

Si on demande pourquoi un certificat auto-signé : la cible est une VM locale sans nom de domaine public. En production réelle (inventaire prod, futur), web_proxy_tls_mode basculerait vers un mode Let's Encrypt — pas encore implémenté, car pas encore de domaine à valider.

15 Rôle : app_runtime

PM2 n'a pas
de module Ansible

Vérifié dans toutes les collections listées : aucune ne fournit de module PM2. Ce rôle contient donc les seules commandes du projet exécutées sans module dédié — chacune gardée selon sa nature.

CommandeGardePourquoi celle-ci
pm2 startup systemdcreates:n'agit que si l'unité systemd n'existe pas encore
npm ci / npm run build / npm prunewhen: + changed_when:rejouées seulement si le checkout a changé, jamais de faux changed=0 silencieux

Le bug qui a failli passer inaperçu. Sur un compte applicatif qui n'a jamais invoqué PM2, la toute première commande démarre elle-même le démon et écrit sa bannière de démarrage ([PM2] Spawning PM2 daemon…) sur stdout — avant la sortie utile. pm2 jlist en aurait hérité, et son from_json aurait échoué avec Expecting value: line 2 column 25. Invisible en rejouant un rôle déjà appliqué (le démon tournait déjà) ; systématique sur machine vierge. Corrigé en insérant pm2 ping avant pm2 jlist : sa propre sortie n'est jamais analysée, peu importe qu'elle porte la bannière.

Conduite

Le sujet proscrit les commandes « sans garde » — pas les commandes tout court. Dis-le explicitement si la remarque vient : chacune des quatre commandes ci-dessus est gardée selon sa nature exacte, ce n'est pas une liste de commandes brutes.

Ce bug-là, raconte-le en entier : c'est celui qui a le plus directement motivé la démonstration de reconstruction complète (slide 19). Une machine « déjà touchée une fois » ne l'aurait jamais révélé.

Si on demande pourquoi ne pas parser la sortie autrement (grep, filtre plus tolérant) : parce que la bannière PM2 n'a pas de format stable garanti d'une version à l'autre — la solution robuste est de ne jamais analyser une sortie qui peut la contenir, pas de deviner son format.

16 Qualité du playbook

Rejouable sans effet,
vraiment

L'idempotence n'est pas un slogan : c'est une propriété vérifiée, module par module, avec les modules natifs Ansible comme garantie de base.

Le cas général

Chaque module Ansible utilisé (apt, template, user, ufw, mongodb_user, mongodb_index…) compare l'état déclaré à l'état réel et ne modifie rien s'ils correspondent déjà. C'est la propriété que le playbook hérite gratuitement, sans l'écrire soi-même.

Le cas assumé : PM2

Sans module natif, l'idempotence de app_runtime repose sur des gardes explicites (slide précédente) plutôt que sur un module qui la garantirait tout seul. C'est la seule zone du projet où l'idempotence est construite à la main, pas héritée — et elle est vérifiée par la CD à chaque fusion (slide 22).

Preuve : un second passage complet de site.yml sur la même cible donne changed=0 — aucune tâche ne modifie quoi que ce soit. Détail dans soutenance/preuves/idempotence-2026-09-08.log, montré en direct à la slide 19.

Conduite

Distingue bien les deux sources d'idempotence : celle qu'on obtient « gratuitement » avec des modules Ansible corrects, et celle qu'il a fallu construire à la main pour PM2. Le jury doit comprendre que ce n'est pas un hasard heureux.

Si on demande comment vérifier l'idempotence sans attendre un second passage complet (1 min 38) : ce n'est pas nécessaire de le faire en direct pendant la soutenance — le journal idempotence-2026-09-08.log en est la preuve déjà rejouée, et la CD le revérifie automatiquement à chaque fusion sur main (slide 22).

17 Portabilité

Trois inventaires,
un seul code

Le runner GitHub,
machine vierge à chaque run

Le VPS mutualisé n'est pas joignable depuis un runner GitHub, et la VM Multipass est locale. Le runner devient donc lui-même la cible : Ubuntu 24.04 neuf, provisionné complet, à chaque fusion sur main.

1Provisionneransible-playbook site.yml -i inventories/ci sur le runner tout juste alloué

3Tests de fumée/health en direct, /health via Nginx/TLS, authentification refusée en 401
Le bug qui n'apparaissait qu'une fois sur deux. Le filtre Jinja2 urlencode ne protège pas le caractère « / » — il le traite comme un séparateur d'URL légitime. Or « / » coupe une URI MongoDB : le pilote refuse la connexion avec MongoParseError: Password contains unescaped characters. Le mot de passe étant généré aléatoirement, le bug n'apparaissait que si ce mot de passe contenait un « / » — environ une fois sur deux. Celui de staging n'en avait pas ; celui du runner CI, si. Sans ce second environnement, le bug serait resté latent. Corrigé par | urlencode | regex_replace('/', '%2F').
Et les tests d'intégration mobile (npm run parcours) ? Cette suite exige un jeu de données seedé (un compte utilisateur existant) que le playbook Ansible ne pose pas ; la jouer sur une machine tout juste provisionnée produirait un échec sans valeur. Elle n'est donc exécutée par aucun pipeline — elle se lance à la main contre une API déjà peuplée. Ce que la CD vérifie à sa place, ce sont les trois tests de fumée bout-en-bout ci-dessus contre l'API que le playbook vient d'installer, dont le POST /auth/login qui renvoie 401 au format d'erreur métier : la preuve que MongoDB est réellement interrogé, pas seulement que Node répond.

Conduite

C'est le bug le plus instructif de toute la soutenance : il ne parle pas de code cassé, il parle de hasard — un mot de passe aléatoire qui contient ou non un caractère piège. Assume-le comme un argument en faveur du multi-environnement, pas comme une honte.

Provisionnement mesuré sur le runner : 4 min 35 s — plus long qu'en local (1 min 38). L'écart précis n'a pas été instrumenté ; deux facteurs plausibles à formuler comme hypothèse, pas comme certitude : le runner GitHub est une machine distante mutualisée, avec des entrées-sorties et une bande passante réseau moins favorables, et l'image Multipass d'Ubuntu 24.04 embarque déjà certains paquets de base.

Si on demande « le CD déploie-t-il en production réelle ? » : non, assume-le explicitement — c'est une limite documentée (slide 26). Le runner est une machine vierge de démonstration, plus exigeante qu'un serveur permanent puisque tout est refait à chaque fusion, mais ce n'est pas encore un déploiement en production.

21 Vérification automatique

changed=0,
ou le pipeline échoue

L'idempotence n'est pas seulement mesurée une fois pour la soutenance : elle est recontrôlée à chaque fusion sur main, automatiquement.

- name: Vérifier l'idempotence
  run: |
    set -o pipefail
    ansible-playbook site.yml -i inventories/ci | tee run2.log

    changed=$(grep -oE 'changed=[0-9]+' ...)
    failed=$(grep -oE 'failed=[0-9]+' ...)

    if [ "${changed}" != "0" ] || [ "${failed}" != "0" ]; then
      echo "::error::Playbook non idempotent"
      exit 1
    fi
Deux garde-fous, pas un seul. set -o pipefail : un échec d'ansible-playbook lui-même ne peut pas se glisser derrière un changed=0 et passer inaperçu. Et l'absence de récapitulatif exploitable fait échouer le contrôle plutôt que de le laisser passer par défaut — la CD refuse de conclure « c'est bon » si elle ne peut pas le prouver.

Conduite

Le message à faire passer : ce n'est pas Clara qui garantit l'idempotence en la mesurant une fois avant la soutenance, c'est le pipeline lui-même qui la garantit à chaque fusion future, sans intervention humaine.

Si on demande ce qui se passe si une régression casse l'idempotence : la CD échoue avec un message explicite (Playbook non idempotent — changed=X failed=Y), la fusion sur main a déjà eu lieu (le contrôle est post-fusion, pas un check de PR — voir slide 8) mais l'échec est immédiatement visible dans l'onglet Actions, à corriger en urgence.

22 Sécurité

Trois couches,
zéro secret en clair

ansible-vault

3 variables chiffrées par environnement : vault_jwt_secret, vault_mongodb_admin_password, vault_mongodb_app_password. .vault-pass jamais committé, transmis hors dépôt.

GitHub Secrets

ANSIBLE_VAULT_PASSWORD, un seul secret dépôt, consommé par ci.yml et cd.yml pour déchiffrer le vault au moment du pipeline.

gitleaks

Dernière étape de ci.yml : détection de secrets sur le diff. Le dépôt est public — c'est la vérification qui empêche une valeur en clair d'y atterrir un jour.

Défense en profondeur côté CD : chaque valeur du vault CI est enregistrée via ::add-mask:: avant de jouer le playbook (GitHub masque alors la chaîne dans tout le journal, y compris dans une trace d'erreur imprévue), et un filtre sed neutralise en plus tout fragment d'URI MongoDB (mongodb://user:pass@ → mongodb://***:***@) dans les journaux de diagnostic. Deux couches, pas une seule pour les yeux.

Conduite

Relie explicitement au bug de la slide CD : c'est parce que les mots de passe passent par une URI construite qu'un caractère mal échappé y a un effet, et c'est pour ça que le masquage des journaux est une seconde ligne de défense indépendante de l'échappement lui-même.

Si on demande comment on prouve qu'aucun secret n'a jamais fuité : gitleaks tourne sur chaque Pull Request depuis la mise en place des rulesets (Tâche 13) — un secret introduit en clair bloquerait la fusion. Pour l'historique antérieur, aucune vérification rétroactive n'a été faite ; le dépôt reste public à revoir si un doute survient.

24 Exploitation

Sauvegarder,
sans exposer le mot de passe

Ce qui tourne

mongodump --archive --gzip, cron root à 03h00, rétention 7 jours. Archives sous /var/backups/mongodb/, 0700 root:root.

Écrit sous nom temporaire

Le dump s'écrit d'abord en .tmp ; set -e arrête le script avant le renommage si mongodump échoue — aucune archive tronquée ne prend jamais le nom d'une sauvegarde valide.

Bug 1 — le mot de passe visible par ps. 0700 protège le script, pas la ligne de commande du processus qu'il lance : passer le mot de passe admin en argument de mongodump l'exposerait à tout utilisateur local (ps aux). Corrigé : lu depuis un fichier de configuration (--config), jamais depuis --password.
Bug 2 — un fichier d'état qui ment. Le script écrivait FAILED en cas d'erreur… sauf tué par SIGTERM (arrêt cron, OOM killer) : sans trap explicite, bash voit dans $? le code de la dernière commande achevée avant le signal, jamais celui du signal. Une sauvegarde tuée laissait donc un OK périmé. Corrigé par trap 'exit 143' TERM et trap 'exit 130' INT, vus ensuite par le trap EXIT.
Restauration testée — 0,24 s, mais ciblée. Document témoin inséré, sauvegardé, supprimé, puis restauré (--nsInclude=logichain.temoin) et retrouvé intact. Pas une restauration intégrale : une seule collection, un volume de démonstration minime. Remesurée pendant la rédaction du Runbook : 0,21 s, cohérente.

Conduite

Les deux bugs de cette slide sont ceux qui parlent le plus directement de sécurité opérationnelle — un attaquant local qui n'a jamais besoin de casser quoi que ce soit, juste de lancer ps au bon moment, et une supervision qui ferait confiance à un fichier d'état faux. Prends le temps de bien les raconter.

Si on demande pourquoi ne pas juste chiffrer le fichier de config temporaire : il est supprimé par le trap cleanup dans tous les cas (succès ou échec), et créé avec umask 077 — la fenêtre d'exposition est déjà minimale sans complexité supplémentaire.

Si on demande pourquoi ne pas avoir testé une restauration intégrale : ça aurait écrasé les données de démonstration réelles (items, events, users) avec --drop, ou échoué sur des clés dupliquées sans --drop. La procédure ciblée sur une collection témoin isolée prouve le même mécanisme sans ce risque.

25 Honnêteté

Ce que je n'ai pas fait,
et pourquoi

CD sur runner éphémère

Le VPS mutualisé n'est pas joignable depuis GitHub Actions, la VM Multipass est locale. Le runner devient la cible. C'est plus exigeant qu'un déploiement classique (tout est refait à chaque fusion), mais ce n'est pas un serveur permanent.

Le VPS Docker/Traefik n'est pas la cible

Il héberge d'autres projets ; Nginx y entrerait en conflit de ports avec Traefik déjà en place. Il reste un héritage du module précédent, pas la destination du playbook.

/docs non protégée

Le fichier .env généré ne définit pas d'authentification basique pour la documentation Swagger de l'API. Sans conséquence sur une VM locale injoignable ; à durcir avant toute exposition publique — la procédure est écrite dans le Runbook.

  • Aucun inventaire prod réellement éprouvé : la structure à trois inventaires existe (slide 18) et ci/staging sont tous deux joués en vrai, mais prod reste une structure anticipée, jamais instanciée ni provisionnée contre une cible réelle — le VPS mutualisé actuel n'en est pas la destination. Recommandation écrite : instancier prod et rejouer site.yml contre elle avant toute mise en production réelle.
  • PM2 sans module Ansible : déjà détaillé (slide 16) — chaque commande y est gardée selon sa nature, pas laissée nue.
Aucun de ces points n'a été découvert par le jury en premier. Un périmètre tenu et documenté vaut mieux qu'un périmètre affiché comme complet et qui ne l'est pas.

Conduite

Slide difficile à assumer à l'oral mais nécessaire : ne t'excuse pas, énonce ces points comme des arbitrages avec leur justification prête, exactement comme en MP3 et MP4.

Si on demande laquelle de ces limites corriger en premier : l'inventaire prod — c'est celle qui bloque le plus directement une mise en production réelle, et rien ne garantit qu'un inventaire jamais joué se comporte comme staging ou ci tant qu'il n'a pas été éprouvé au moins une fois.
